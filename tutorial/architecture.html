Les principes de conception

🔀 Séparation API / exécution

L'API ne fait qu'accepter et enfiler. Elle répond instantanément ; le travail lourd part dans la file de messages.

📦 Workers stateless

Tout l'état d'un run vit en base. Un worker ne garde rien localement, donc on peut en ajouter ou en tuer librement.

✉️ Découplage par messages

RabbitMQ absorbe les pics (backpressure) et garantit qu'un run non terminé est repris si un worker tombe.

🧬 Cœur agnostique

Le moteur dépend de traits, pas de Slack ni de Postgres. On ajoute un connecteur sans toucher à l'orchestration.

La même chose, en crates Rust

crates/
├── core/         # types, traits & erreurs partagés (agnostique)
├── engine/       # moteur DAG (séquence, conditions, boucles, //)
├── connectors/   # Slack · Gmail · Notion · GitHub · HTTP + SDK
├── api/          # serveur HTTP axum (auth, CRUD, /metrics, OpenAPI)
└── worker/       # pool d'exécuteurs (consomme la file → moteur)
