Du clic au résultat, fiable par défaut

Le parcours réel dans l'application, et pourquoi un crash de worker ne perd jamais une exécution.

Le cycle de vie, étape par étape

Ce qui se déroule entre le déclenchement et le résultat.

① Enfilement

Le trigger crée un run et le pousse dans RabbitMQ. L'API répond immédiatement — elle ne bloque jamais sur l'exécution.

② Consommation

Un worker stateless du pool tire le message. N'importe quel worker peut le prendre : aucun état local.

③ Déroulé DAG

Le moteur exécute les nodes dans l'ordre du graphe (séquence, branches if/switch, boucles loop/while), en résolvant le templating.

④ Checkpoint

Après chaque node, l'état (sorties + prochain node) est écrit en PostgreSQL. Le run est rejouable depuis ce point.

⑤ Reprise

Worker tué en plein run ? Le message non-acquitté retourne dans la file ; un autre worker reprend au dernier checkpoint. Rien n'est perdu.

⑥ Observabilité

Métriques Prometheus sur /metrics, dashboards Grafana provisionnés, journal d'audit des actions.

Le scénario de panne. Imaginez le run arrêté à la node gmail_send (l'email est parti, le checkpoint est écrit), puis le worker crashe. RabbitMQ n'a pas reçu l'acquittement → il remet le run en file → un autre worker le reprend à partir de notion_create, sans renvoyer l'email. Idempotence par checkpoint.
